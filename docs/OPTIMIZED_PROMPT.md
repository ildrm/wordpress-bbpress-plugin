# Optimized implementation prompt: Forum Intelligence for bbPress

## Objective and authority

Implement a complete, production-quality bbPress intelligence plugin without modifying bbPress or WordPress core. ORIGINAL_PROMPT.md is the authoritative 124-section acceptance catalog. This optimized prompt removes repeated direction, preserves scope and makes acceptance evidence explicit. Do not downgrade omitted detail to optional: consult its original section.

## Execution sequence

1. Inventory the repository, native versions, deployment constraints and authoritative APIs. Preserve existing user changes. Record verified facts and assumptions.
2. Build lifecycle/schema/access/operation/REST foundations and a tested solutions vertical slice.
3. Add engagement/moderation, local search/duplicates and async indexing.
4. Add optional semantic/RAG/knowledge with public-only evidence, source hashes and human editorial controls.
5. Add reputation/domain expertise/discovery/follows/notifications.
6. Add composer fields/templates/drafts/scheduling/files/polls and optional messaging/polling/PWA/push.
7. Harden each slice, then run the original release matrix and fourteen self-review passes. Close requirements through traceable tests and actual observed behavior.

## Nonnegotiable invariants

- bbPress owns posts, capabilities and visibility. Native nonce/authentication checks never replace authorization.
- Reauthorize current sources at retrieval, caches, snippets, counts, citations, graph edges, feeds, files and delivery. Include ancestor/password/group restrictions and post moves/status changes.
- Keep AI optional. Restricted content does not leave the site by default. Only explicitly opted-in public fields enter external processing. No tools, AI punishment or automatic publication.
- Treat source/provider text as untrusted data. Ground only sent current citations; abstain with useful search/posting options when evidence cannot answer.
- Preserve solution/audit history, editorial manual locks and user ownership. Atomic reversible counters, optimistic conflicts, unique identities and leased bounded queue work protect consistency.
- Protect bytes, not merely attachment links. Label public URLs honestly. No private-content browser/PWA cache, raw-query telemetry or hidden remote reporting.
- Use maintained verified dependencies with TLS validation, current advisories, licenses and reproducible builds. Secrets stay in protected server configuration.
- Native progressive forms and accessible semantic markup work without JavaScript. JavaScript enhances without blocking ordinary posting. Mobile, RTL, keyboard and theme compatibility are acceptance gates.

## Verification discipline

For each module: design → implement → static/unit/integration → adversarial/current-permission review → applicable UX/a11y → regression → refactor → documentation. Test behavior rather than implementation mirrors. Use real native sources and actual WordPress/bbPress databases. Separate mocks from live credentialed external tests.

Test anonymous/participant/author/spectator/blocked/moderator/admin against public/private/hidden/password and ancestor/group access. Recheck after source edits/moves/status/privacy changes. Verify activation/deactivation/migration/preserve/opt-in uninstall, multisite, classic/block themes, no-AI/live-AI/outage, delayed cron, REST, privacy export/erasure, mobile/RTL and keyboard. Benchmark cold/warm queries, candidate bounds, high-subscriber fanout and existing large installations.

Run Composer validation/audit, PHP syntax/WordPressCS/static analysis/PHPUnit, frontend lint/tests/build, browser/a11y and native integration in CI. Production dependencies and built assets must match the lock/source; inspect a clean installable artifact.
