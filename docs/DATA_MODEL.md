# Data model

Schema version 8 creates eleven `{$wpdb->prefix}fi_*` tables using idempotent dbDelta migrations and InnoDB. Site prefixes isolate network sites. Shared WordPress user tables are referenced through native wpdb properties.

| Table | Ownership and purpose | Key guarantees |
| --- | --- | --- |
| solutions | Topic solved state, accepted IDs, primary, last actor/time/version | One row per topic; optimistic version plus row lock |
| signals | Votes, reactions and confirmations | Unique object/member/kind; indexed object totals |
| events | Audit and reversible reputation ledger | Stable optional event key; actor/subject/source and points; subject/source aggregate index |
| links | Accepted links, relationships, follows/mutes, messaging membership | Unique relationship identity; source/user/target indexes |
| notifications | Per-member source notification | Unique member/event delivery; read-state, chronological, category and mail indexes |
| cases | Human report and moderation queue | Unique source/reporter; status/priority queue |
| jobs | Async payload, revision, attempts, lease and safe error code | Unique coalescing key; claim and lease indexes |
| chunks | Derived searchable source text, hash, visibility, canonical JSON vector/model and nullable compiled vector cache | Source PK, FULLTEXT, forum and vector-candidate indexes |
| records | Typed bounded state: summaries, credits, polls/votes, drafts, files, conversations/messages, push, feedback, saved searches, moderation advisories | Unique record key; owner/kind, source/kind and kind/ID keyset indexes |
| metrics | Aggregate UTC day/event counts | Day/kind primary key; no query text |
| limits | Atomic abuse/provider quota buckets | Hashed identity/window primary key |

JSON records are domain validated, not an arbitrary document write API. Their IDs must not be confused with WordPress post IDs: conversations and message notifications use record IDs; content signals and other source notifications use native post IDs. Notification kind selects the source namespace before permission checks.

Options: `fi_schema_version`, `fi_settings`, `fi_field_definitions`, `fi_templates`, `fi_template_variants`; a temporary non-autoloaded `fi_vector_cache_upgrade` marker schedules legacy cache conversion. Notification preferences use site-scoped `_fi_preferences_{blog_id}` user meta. Topic field values and knowledge provenance use `_fi_*` post meta. Push credentials are sealed with Sodium using a site-scoped key derived from WordPress salts.

Solutions normalize accepted links for reverse invalidation while retaining immutable change events. Poll choices/counts and vote records update under the poll lock; erasure uses that same lock. Uploads serialize using a unique attachment lock record. Privacy signal erasure locks and deletes an exact batch with credit reversals in the same transaction. Reconciliation re-reads locked signals to avoid awarding credit from erased snapshots. Credit targets and daily budgets update atomically, preserve reversals and transfer existing credit ownership when reconciled.

Database backups must include custom tables, WordPress metadata/options, attachment storage and the protected server configuration needed to decrypt retained push credentials. Salt rotation intentionally invalidates push subscriptions.

Saved searches hold the owned query, whitelisted filters, an explicit `alerts` flag and opt-in timestamp. Publication markers contain no query or owner and enforce first-publication semantics until the native source is permanently deleted. Alert jobs scan `(kind,id)` ranges capped at the event's saved-record boundary, lock/re-read each current query and deduplicate notification delivery by member/native source. No schema table is added by version 6; its idempotent migration adds the kind/ID records index.

Version 7 adds `(user_id,id)` and `(user_id,kind,id)` notification indexes for bounded chronological and category views. It adds no tables or copied content. The unread summary reads at most 500 owned unread candidates, reauthorizes distinct source/kind pairs once within that request, and stops after 100 authorized items. It does not persist a visibility-sensitive aggregate count.

Mention fallback adds no table or copied identity state. It uses existing limits and notification event-key uniqueness. Recipient handles are resolved from current native WordPress users at delivery; lookup is bounded/current-site and only returns currently eligible recipients. A given source/member fallback mention is delivered once across publication/edit retries. Request-local content hashes prevent repeated hook processing within one request; they are never persisted.

Configuration audit uses the existing events table and retention/erasure policy. Successful native setting changes contain only sorted known field names; template/field updates contain definition counts. Export/import events contain no transferred configuration body. Unchanged settings and sanitizer calls create no successful-change record. There is no schema change for these events.

Contextual question templates are bounded site options, with at most 20 plain-text definitions and three optional criteria per rule. Read responses contain only global/current-forum guidance after current native authorization. Optional selections remain in the composer page; they are not stored on topics, in records, or in analytics. Configuration audit records definition counts. Reviewed import rolls options back atomically, including their prior absence. Default uninstall preserves the option; explicit deletion removes it. This adds no table or schema migration.


The schema 7→8 migration adds nullable `chunks.vector_binary` (LONGBLOB) without rewriting canonical JSON, native hashes or editorial records. FIV1 frames contain a big-endian 32-bit dimension count, little-endian double squared norm and scaled components, followed by a SHA-256 checksum of the exact JSON bytes, a NUL delimiter and the payload. Dimensions are 1–4,096; an eight-byte-double platform produces frames of 56–32,816 bytes. Encoding checks that double size and falls back to JSON on unsupported platforms. Frames use the existing independently scaled cosine arithmetic, with no float32 quantization. Checksums detect cache damage or JSON/frame mismatch; they are not an authentication boundary against a privileged database writer.

Reads verify version, length, dimension bounds, checksum, finite component bounds and exact squared norm before using a frame. Missing or invalid frames fall back to validated JSON without writing. Current model, native hash, access policy and fifty-row/thousand-candidate bounds still apply. Vector writes update JSON, model and compiled frame together under the existing source/hash condition; source invalidation clears both representations. Binary writes bind hex strings through UNHEX to preserve bytes across connection encodings.

Existing installations schedule a coalesced `vector_encode` maintenance chain after successful migration; each job scans at most fifty source rows. The job compiles only current public/model/hash-valid JSON and uses an exact-byte JSON/model/hash compare-and-swap. It neither re-embeds nor rewrites source JSON and can safely retry. Maintenance remains registered with a replacement vector adapter, because the local table is still owned by the plugin. Fresh installations create the column without scheduling a legacy scan. Queue failure/retry controls apply, and full opted-in uninstall removes the pending marker with owned tables.


Summary selection version 2 records the exact evidence_ids, a recent_window_with_accepted coverage label and a versioned fingerprint over source hashes, accepted-state version and origin forum. Provenance includes the topic, at most fifty recent native published replies and at most ten accepted replies outside that window (61 sources maximum). Transfer is at most twelve sources: question, all current accepted replies, then evenly sampled remaining bounded discussion; reply order follows native UTC publication date and ID. Primary/accepted role labels and publication chronology precede the ordinary bounded/redacted public text. The native Indexer hash and vector model/schema remain unchanged. Old summary fingerprints become stale for review; human text/locks and existing native article provenance are retained rather than rewritten. No complete-long-thread coverage claim is made.

Discussion revision markers use existing records with kind knowledge_source_revision, key knowledge_source_revision:<topic>, owner 0, native topic object ID and empty JSON payload. Atomic inserts/increments produce a monotonic version per current blog; the exact increment count has no product meaning. There is no source-content copy, schema migration, generation job or provider call. Creation, meaningful native edits, permitted field/hierarchy metadata, terms and deletion update affected native topic markers; native bookkeeping/indexing does not. Topic deletion removes the marker even after child cleanup.

Summary/article fingerprint version 3 incorporates discussion_revision alongside the existing bounded source hashes and accepted state. selection_version remains 2 and native Indexer hashes/vector storage remain unchanged. Article _fi_provenance stores renewed source hashes/fingerprint plus fingerprint_version, discussion_revision, verified_at (UTC) and verified_by after explicit human review. Authored native title/body and the separate summary record/manual lock are preserved. A knowledge_verified audit event stores only the article ID, source topic and actor; a unique opaque event key deduplicates unchanged actor/source/body review. Native metadata and audit writes are transactional; rollback clears the WordPress metadata cache. Default uninstall preserves these owned records and article metadata under the existing retention policy; opted-in complete deletion removes owned tables and provenance metadata, clears native metadata caches, and retains authored knowledge articles and native forum content with WordPress.

Automatic summaries reuse the jobs table with kind summary_auto, key summary_auto:<topic> and payload containing only the native topic ID. The configured actor and numeric policy remain in current site settings, rather than a stale copied job payload. Native discussion revision and accepted-state events coalesce one delayed topic job. The native published-reply admission query stops at the configured threshold (at most 5,000 rows); it copies no bodies. The existing revision updated_at supplies the current quiet period and summary generated_at supplies the minimum interval. Jobs requeued while running use the existing revision/lease mechanism. Execution renews current policy; provider/result admission guards reject revoked settings/authority without replacing the saved summary. Settings belong to ordinary reviewed export/import/defaults and existing preserve/opt-in uninstall policy. There is no schema or native index/vector change.

Responsible-editor alerts reuse jobs with kind knowledge_review and keys knowledge_review:<topic>:<cursor>. Payload contains only the native topic and article-ID cursor. A 120-second initial delay coalesces native source changes; each keyset job selects at most 25 current source-bound fi_knowledge articles and primes native posts/metadata before checking them. Cursor continuation has a separate identity, preserving a restarted initial job during concurrent source events. No copied article body/title or saved editor list is added.

Notifications use kind knowledge_review with object_id in the native article namespace and current native author as user_id. An opaque event key combines article ID, current discussion revision/accepted-state version, recorded provenance fingerprint and owner, deduplicating a repeated unchanged review job. Current visibility validates owner, supported native state, native editing rights, all provenance sources, stale state, source mutes and current module/alert policy. The same rule guards inbox/count/email/push. Presentation uses a generic label and native editor URL. The category joins existing per-site preferences and retention/erasure; it is excluded from important-only mail. The optional site flag belongs to existing reviewed configuration/defaults/preserve/explicit-deletion policy. Schema remains 8.


Automatic article conversion adds no schema or table. knowledge_auto_draft jobs contain only the current-site topic ID and use a coalesced topic identity. A native topic-row transaction serializes automatic copies. Current source-bound native knowledge posts (including trash) suppress conversion, while the existing source/provenance metadata and native revisions are reused. A failed native insertion guard rolls back the new native rows and invalidates its positive post/metadata caches, at most the bounded recorded source caches, the configured actor and current-site policy option caches. Author, source and policy are resolved from current storage; no article body/title or recipient list enters the job.


Checkpoint 92 adds optional source_text_hashes and solution_version to source-bound summary/article provenance. Digests use SHA-256 over length-prefixed UTF-8 bytes of the native title, content and excerpt; no historical body is stored in comparison results. The existing fingerprint version remains 3 and schema remains 8. Human verification renews these ancillary baselines. Legacy records remain readable under existing strict native source checks and never acquire a fabricated revision baseline. Revision pointers are bounded, current-permission native admin links and are not exposed as a public REST feature. Automatic draft admission checks current-site table metadata for InnoDB before entering its existing native row transaction.


Moderator recommendations reuse current-site records and its existing kind/id index; schema remains 8. A unique knowledge_recommendation:<topic> key moves among knowledge_recommendation, knowledge_recommendation_withdrawn and knowledge_recommendation_drafted kinds. Payload stores the sanitized bounded human reason, at most 64 native source hashes, discussion revision, accepted-selection version, original recommending user and an article ID after conversion. There is no copied native source title/body or AI result. The owner remains the note author through withdrawal/conversion; existing privacy erasure removes their record. Audit events identify the acting moderator and optional article, with no reason text.

Writes lock the exact current-site key and compare its kind/id/version against the admitted record. Unexpected kinds or changed versions cannot be overwritten. Every recorded previous and current source and current moderator/module policy are renewed before and after native callbacks. Rollback clears the union of bounded previous/current source caches plus actor and policy caches. Malformed scalar legacy payloads are withheld. Active queue reads use descending ID keyset pagination: 26 candidates for a maximum 25 rows and an older cursor; inaccessible rows are withheld without unbounded backfill. Rendering renews record state, policy and source permissions. Native topic deletion removes only its recommendation kinds. Default uninstall preserves private notes; explicit full data deletion removes their owned table while retaining authored native forum/article content.


Selected knowledge target adapters add the administrator setting knowledge_target (default fi_knowledge) and article metadata _fi_knowledge_target containing the registered adapter identifier. Existing built-in articles without that marker retain the default binding. Source/provenance/editorial fingerprint formats and schema remain unchanged. A transient exact _fi_draft_token identifies the newly inserted native copy during validation and is removed on success; native IDs predating insertion cannot be reused by conversion. Draft insertion, provenance, recommendation archive and audit participate in the existing transaction. Rollback clears created/source/actor/current-policy caches; ownership recovery of a genuinely new marker-bound copy does not depend on a callback leaving its author/status unchanged. Native content/metadata/owned tables follow existing preservation and explicit-deletion policy.

Adapters are resolved from the current registry and current site settings at each admission. Only registered private native editorial types with title/editor/author/revisions, mapped capabilities, UI enabled and public queries/search/REST/archive exposure disabled are eligible. Owner and native draft type/state/capabilities are renewed after callbacks. Owned provenance/source/adapter metadata continues to identify guarded content after selection changes or adapter removal; incompatible or absent adapters withhold presentation while retaining authored storage. Source-review alerts use at most 25 eligible native article IDs per keyset job across registered target types, with current author/source/permission checks. Automatic duplicate suppression follows source binding across prior target types.

## Canonical stored summary integrity

Schema remains 8. Summary records require kind summary, canonical summary:<topic> key and matching current native topic object_id. Raw payload JSON is decoded at the domain boundary rather than treating falsy scalars as empty data. Ordinary policy/generation requires an associative payload with typed boolean flags and valid bounded content where present. Displayable content has a nonempty string answer up to 20,000 characters, a 64-hex fingerprint and at most 64 native source/hash pairs including the origin topic; source types/context/current access are renewed. Damaged content is retained and withheld. A deliberate moderator edit can repair a known scalar payload, while foreign kind/object bindings and uninterpretable source proofs are refused.

Persisted ID/kind/key/owner/object/version/payload identify the original summary snapshot. Generated completion and manual writes lock the canonical current-site row and compare this snapshot after native permission/source callbacks. A competing first generation or newer human edit followed by unlock cannot be overwritten by an older completion. Summary data and its audit event share a transaction. Rollback refreshes bounded prior/current source, actor and policy caches; privacy erasure and default retention continue to use the preserved original owner. No native article content, source history or schema migration is introduced by repair.

## Reaction configuration and retention

The current site's fi_settings.reactions is a bounded array drawn from like/helpful/insightful/thanks, in catalog order. Absence uses the default four choices; an explicit empty array disables new reactions. Malformed scalar or oversized selections enable none. Native checkbox submission uses a transient reactions_present marker to distinguish an unchecked group; the marker is excluded from stored configuration/export. Partial settings sanitation without a group preserves the existing selection.

Signals stay keyed by native object, actor and kind reaction_<id>. Disabling a choice retains history and reputation credits. Zero withdrawal of a disabled choice requires an existing row for that actor; unknown kinds and unowned withdrawals cannot create history. Participation, current source visibility and reaction configuration are renewed inside the signal transaction. Refusal rolls back writes and refreshes affected native post/user/options caches.

## Native vote admission and nested transactions

Signal writes renew the current site's module, downvote and self-vote policies inside their transaction. The native source's site/type/author/status/password/topic/forum/parent/ancestor binding and every native parent's state must still match the reviewed source, including after row-lock callbacks. The actor's current native role/capability/status context is compared and participation is admitted again before writing. Credits use the raw native author, independent of presentation filters. Positive confirmations admit only a currently solved row with a bounded integer list of accepted native replies, read under row locking rather than a display cache.

Store coordinates transactions across service instances sharing the same native wpdb object. An outer operation owns START/COMMIT/ROLLBACK; nested operations use unique connection-scoped savepoints. A nested exception rolls back its own writes even if the outer caller handles it; an outer exception rolls back all completed nested writes. Coordinator state is released on completion and kept in a WeakMap to avoid retaining database objects. Storage still requires transaction-capable tables. Domain handlers refresh affected WordPress caches and the matching current-user object after native callback rollback; savepoints do not themselves undo arbitrary plugin memory or external side effects.

## Duplicate suggestion feedback

A bounded browser offer contains version 1, current site/account/forum IDs, issue time, a random nonce and at most five current topic IDs. It is HMAC-signed with the native nonce salt, expires after fifteen minutes and contains no title/body/tags/field text. Feedback is authenticated through ordinary native REST cookies/nonces; current participation, composer policy, forum/source types/binding/access are renewed before and inside the transaction. Guests receive ordinary local suggestions with no feedback offer.

Each viewed/opened/dismissed outcome claims an opaque SHA-256 bucket in the existing limits table, using the offer issue time as window_start and count 1. The table's primary key prevents concurrent replay inflation. Only an offered topic may be acknowledged as opened. Claim insertion and the daily aggregate metric commit together; a metric failure rolls back the claim so a genuine retry can succeed once. No offer payload, query, source ID, account ID, draft or per-user event is stored by this attribution path. Claims use the existing two-day bounded limits cleanup; daily totals follow existing operational retention. Feedback is limited to ninety requests per account per minute. Schema stays at version 8.

## Generated-answer feedback receipts and review records

The site/account-prefixed `fi_answer_feedback_USER_TOKEN` transient holds a version-1 receipt for 900 seconds: site, reader, issuance time, topic, qualifying source, accepted primary, bounded source IDs/hashes and a SHA-256 response fingerprint. The token contains 128 random bits. The receipt holds no question or generated answer text; the existing owner result transient separately retains display data for five minutes.

A submitted `ai_feedback` record has key `answer_feedback:USER:RESPONSE`, owner equal to the reporting reader and object equal to the native topic. Its eight payload keys are version, value, state, response, source, primary, sources and reviewed_at. The five categories and open/resolved/dismissed states are whitelisted. Source fingerprints bind the response version; no prompt/answer is copied into this record. The native records table starts at version zero. Submission/update and its audit event commit atomically; reviews lock the row and compare the submitted version, update status/UTC time and write a separate audit event. Reviewer identity lives in the existing audit actor field, avoiding a redundant personal reference in the report.

Existing source-only feedback is retained for normal export/retention but is not presented as verified response feedback. Owner records are included in the native privacy exporter and deleted by the eraser; operational audits are anonymized under the existing policy. The configured retention batch includes `ai_feedback`. No new table/schema version is needed.

Relationship writes and their audit events now share one transaction, with renewed native source types, actor and endpoint permissions. Privacy export also includes human relationship creator metadata; erasure replaces that personal creator reference with zero while preserving the approved edge and native editorial content. Legacy malformed JSON is excluded safely from this creator lookup.
