# Development and verification

Use an isolated WordPress installation and disposable database. Tests reset plugin tables and create/delete owned native fixtures. **Do not connect a production site.**

1. Install PHP 8.2+ with OpenSSL, Sodium, mbstring, mysqli, curl, fileinfo and XML; Composer; Node 24; MariaDB/MySQL with InnoDB and FULLTEXT.
2. composer install, npm ci, npm run build.
3. Download stock WordPress into .runtime/wordpress and official bbPress source into .runtime/bbpress. Activate the linked/copied plugin and bbPress in the isolated installation. Create administrator fi_admin with a test-only password and email.
4. Obtain official WP-CLI as .runtime/wp-cli.phar. Run php tools/verify-cli.php to extract its real class for static analysis. No fake CLI function declarations are used.
5. Download BuddyPress 14.5.2 into .runtime/bp-source/buddypress, install/activate it and enable the groups/members/activity components for compatibility tests. Static analysis scans the actual root-blog function source.
6. Set FI_WP_PATH to the isolated installation if it differs from .runtime/wordpress. On Windows, set OPENSSL_CONF **before starting PHP** to the actual openssl.cnf. The test bootstrap's putenv cannot repair OpenSSL already initialized without EC configuration.
7. Run Composer validation, tools/lint.php, PHPCS, PHPStan, PHPUnit and tools/integration.php. Run npm lint/test/build.
8. php tools/seed-e2e.php creates browser-owned fixtures. Serve the isolated site on loopback 8898 with tools/serve-router.php; npm run e2e uses installed Chrome on Windows or Playwright Chromium elsewhere. Set FI_BROWSER to override.
9. Run browser tests sequentially after PHP tests; they share fixtures/schema and must not race. Repeat classic and block themes and scoped axe checks. Network integration uses a separate isolated network database.

Playwright reports/traces, test runtime configuration, database files and credentials stay in ignored .runtime. The router blocks development folders exposed through the source junction. Source assets reproduce the checked-in build; assets.test verifies byte equality.

The PHP integration suite mocks provider HTTP and Guzzle push transport while exercising actual WordPress, database state, cryptographic Web Push framing, source permissions and current membership. These mocks do not demonstrate real external provider or browser-vendor delivery. Full deployment checks are separate.

CI runs the applicable commands in an isolated service database. A workflow definition is evidence of intended gates, not evidence of a completed hosted matrix run.

On a clean Linux CI checkout, tools/setup-tests.php provisions the disposable site and links official sources. It refuses existing wp-config.php to avoid overwriting unrelated installations. Configure FI_TEST_DB, FI_TEST_DB_USER, FI_TEST_DB_PASSWORD, FI_TEST_DB_HOST and FI_WP_VERSION. tools/setup-buddypress.php runs through WP-CLI eval-file. Windows symlinks may need directory junctions; the local prepared runtime already uses them.

Production packaging uses tools/package.php. Run node tools/fetch-scoper.mjs first; the build pins PHP-Scoper 0.18.19 and verifies its official release SHA-256 before execution. Only dependency namespaces are prefixed; the plugin's public namespace and WordPress APIs remain unchanged. The package includes isolated runtime dependencies, preserved license files and a sorted SHA-256 manifest, with no development libraries. ZIP replacement is atomic. The source checkout uses normal Composer dependencies for development.

Native release verification tools require a separate disposable release-wordpress installation on port 8899 and actual extracted ZIP classes. release-smoke.php validates all hashes, lifecycle and core flows; release-push.php exercises prefixed cryptography with preloaded conflicting library names and mocked vendor HTTP responses. release-fixture.php plus the opt-in release-attachments browser suite tests genuine multipart/protected bytes. release-uninstall.php stages must execute in separate processes because WordPress uses include_once for uninstall files. performance.php builds and cleans 1,002 owned topics plus 5,000 synthetic signal rows, records cold/warm query counts and query plans, and reproduces candidate starvation. These tools refuse the primary or a production site.

The opt-in PWA browser checks run with `FI_PWA_E2E=1 FI_PHP=php npx playwright test tests/E2E/pwa.mjs` after ordinary browser tests, never alongside PHP tests. On Windows set FI_PHP to the installed PHP executable. The owned port-8898 fixture restores settings and removes its exact temporary foreign worker after the run. Checks cover manifest/icons, activation, generic offline responses, empty content caches and preservation of a different worker with the same query flag. Desktop installation still requires a manual check.

`tools/network-uninstall.php` uses separate `seed`, `remove` and `restore` processes against the owned two-site `network.example.test` fixture. It verifies root-blog deletion with second-blog preservation, native content, schedules and metadata cache invalidation. Run restore even after a failed remove stage. Its explicit ownership guard intentionally prevents use on another network; it is not a general production maintenance command.

For the owned packaged notification workload, run `php tools/notification-performance.php seed`, `run`, then `restore` in separate processes. The tool refuses a non-loopback release installation and checks that actual packaged classes are loaded. Always restore in a finally block. It creates 201 owned followers, validates nine current exclusions and batch retry deduplication, then checks source privacy after delivery. Its measured cold time excludes fixture creation; larger workloads remain a separate release gate.

The actual saved-search privacy race fixture uses `php tools/saved-search-race.php seed`, then separate `consumer` and `erase` processes. The consumer pauses in a WordPress query filter while holding its query row; `probe` confirms an actual InnoDB lock wait. An owned `.runtime/saved-search-race-TOKEN.release` marker releases the consumer, and `verify` checks zero retained queries/notifications. Always join both processes before `restore`. This is a guarded disposable-package test, never a production workload command. A local orchestrator is `.runtime/run-saved-search-race.mjs`; `.runtime` helpers are not shipped.

## Isolated local PHP compatibility matrix

The 2026-10-07 local container verification uses official PHP 8.4 and PHP 8.2 image digests and MariaDB 11.4, narrow read-only source/native-runtime mounts, disposable labelled databases, an internal Docker network and no published ports. Native WordPress source comes from the verified local 7.1/6.6 trees rather than the WordPress version bundled in the image. Configuration, uploads, PHPUnit caches and database files remain disposable. Mocked push transport needs a public DNS mapping for the approved fixture hostname because the internal network intentionally lacks external DNS access. No live push or AI request is made. Each run verifies resource labels before removing only its own containers and network.

Notification regressions cover current ownership/roles/mutes/source privacy, typed category/read filters, bounded large hidden-candidate scans, source-check reuse, safe date groups and absence of private counts in server-rendered indicators. `tests/E2E/notifications.mjs` exercises native filtering/read/delete on plain permalinks, authenticated no-store summary rendering, scoped accessibility and mobile RTL on both themes.

WordPress hook objects are mutable. Native integration cases clone the baseline hooks before registering test services, then restore them and reset the REST test server afterward. This prevents service/route callbacks from accumulating across cases; the expanded suites pass under the container's unchanged 128 MB memory limit. Release fanout, attachment, privacy-race and uninstall fixtures share a disposable database and must run sequentially. Guards reject an already-active competing fixture before mutation; fanout cleanup verifies its exact synthetic usernames and native source ownership before deletion.

Mentions: `tests/E2E/mentions-managed.mjs` verifies actual BuddyPress autocomplete and that private plugin vendor files remain inaccessible through the development router. `mentions-fallback.mjs` runs only with `FI_FALLBACK_MENTION_E2E=1` and BuddyPress disabled on the disposable main browser installation; it checks native publication, authorized delivery, selected text preservation, no-store lookup failures, keyboard behavior, axe and mobile RTL. The owned publication is removed through `tools/cleanup-mention-fixture.php`, including after a redirect failure by exact synthetic title/author/forum validation.

For native TinyMCE compatibility, run `php tools/mention-editor-fixture.php enable`, then `FI_RICH_MENTION_E2E=1 npx playwright test tests/E2E/mentions-rich.mjs` with BuddyPress enabled and again with it disabled. Always reactivate BuddyPress and run the fixture's `restore` command afterward. It verifies its loopback installation, exact fixture bytes, directory containment and ownership option before modifying the owned mu-plugin. These mutations must not overlap main PHP/browser runs. CI includes these sequential fixtures; a local pass is not a hosted CI result.

The managed-owner PHP regression simulates an external owner through `fi_mentions_managed` while disabling BuddyPress email side effects. BuddyPress 14.5.2's activity-only email callback calls its deprecated notification facade even when the notifications component is absent; that upstream configuration path is not counted as verified by the simulated-owner regression.

Native mention regressions exercise actual bbPress post edits, BuddyPress activity saves and native unread metadata. A test-only native notification filter captures eligible recipients and stops before the upstream deprecated email facade; it does not replace recipient parsing or unread updates. Group cases record and explicitly assert bbPress's known deprecated `bp_get_group_permalink` call, suppressing only that named warning within the fixture; all other deprecations retain their normal behavior. No third-party source is modified. These checks verify topic/reply/group mapping, blocked/muted/current access, revocation between save phases, native quotas and mass-recipient limits, ordinary activity ownership and zero duplicate FI alerts. Live SMTP/notifications-component combinations and retrieval of existing native unread state remain owner/staging acceptance gates.

Encrypted composer copies: npm test uses real Node WebCrypto with isolated in-memory storage. The ordinary browser matrix includes offline-drafts.mjs; it exercises offline saving, authorized online sanitized recovery, passphrase/network separation, expiry/storage failures, native form validity, keyboard/Enter, scoped axe, mobile RTL and guest exclusion. For native TinyMCE, enable the owned editor fixture, run FI_RICH_DRAFT_E2E=1 npx playwright test tests/E2E/offline-drafts.mjs --grep 'rich editor', and always restore the fixture. The installed release check is FI_RELEASE_E2E=1 FI_PHP=php npx playwright test tests/E2E/release-drafts.mjs; it seeds/restores only the disposable release site and must run sequentially with all other release fixtures. Neither local checks nor crypto primitive tests certify external staging, hostile same-origin scripts or secure browser memory erasure.

Composer tools: native tests assert current identity/access/posting, blocked/closed/hidden source denial, inert formatting, Unicode/request bounds, 20/minute quota, no HTTP/provider/content persistence and native-redirect rejection before dispatch. Node selection tests exercise Unicode/surrounding bytes, literal code and invalid ranges. composer-tools.mjs covers selected formatting, roving keyboard/RTL, inert preview with no external-media requests, close focus, stale responses after edits, failed requests/native posting controls and no-JavaScript/guest behavior. Await native textarea focus after a mode switch; WordPress restores its HTML selection with a 100 ms timer. Do not weaken the sandbox to permit test injection. Always restore the owned fixture; no manual screen-reader certification is inferred.
